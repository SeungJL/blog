카공지도는 화면 하나였다. 지도를 깔고 그 위에 필터·드로어·팝업을 전부 얹었다. 랭킹은 아카이브 페이지 안쪽에, 카페 목록은 눌러야 열리는 드로어에 있었다.

여기에 하단 탭과 상시 카페 리스트를 넣었다. 커밋 하나에 16개 파일, 1,422줄이 들어가고 382줄이 빠졌다.

## 바꾼 것

- 하단 탭을 [랭킹·스터디·커뮤니티]로 재구성하고 랭킹·커뮤니티 페이지를 따로 만들었다. 아카이브 페이지는 없앴다
- 지도 아래에 항상 떠 있는 카페 리스트 시트(`CafeListSheet`, 477줄)를 새로 만들었다
- 상단 필터를 콘센트 많음(`power ≥ 4.5`)·자리 여유(`space ≥ 4.7`)·심야 운영·분위기 좋은·주차 가능으로 바꾸고, 나머지 여섯 개(와이파이·단체석·좌석 편한·가성비·화장실 깨끗·시간제한 없음)는 [기타] 바텀시트로 내렸다
- 별점 4.0+ 는 원형 토글로 분리했다

필터를 다시 붙이면서 기존 버그 두 개가 드러났다. '콘센트 많음'이 단체석 조건으로 나가고 있었고, '분위기 좋은'은 심야 운영과 같은 값으로 필터링되고 있었다. 필터가 지도 위에 흩어져 있을 때는 어느 버튼이 무엇을 거르는지 눈으로 대조할 자리가 없었다.

## 바텀시트는 핸들에서만 끌렸다

리스트를 상시로 띄우자 곧바로 문제가 됐다. 그때까지 바텀시트는 최상단 핸들 줄에서만 드래그됐다. 드래그 리스너를 `touch-action: none` 인 헤더에만 붙여 스크롤 영역과 DOM 상 분리하는 방식이었기 때문이다. 목록을 위로 밀어도 아무 일이 없었다.

같은 터치를 목록 스크롤로도, 시트 드래그로도 해석할 수 있다. 둘 중 무엇인지 정해야 한다.

`useSheetBodyDrag`(232줄)는 시트를 움직이지 않는다. 판정만 하고, 확정되면 호출부가 이미 갖고 있는 드래그 엔진을 부른다. 본문 스와이프가 핸들 드래그와 똑같이 동작하는 게 구조로 보장된다. 두 엔진(높이·2단계·고정 임계 / offset·3단계·속도)은 모델이 달라 합치지 않았다.

가로챈 뒤 네이티브 스크롤을 멈출 수단은 `preventDefault` 뿐이다. `touch-action` 은 제스처 시작 시점에 확정돼 도중에 바꿔도 소용없고, `overflow: hidden` 은 `scrollTop` 이 튄다. 그래서 `cancelable` 윈도우 안에 머무는 게 관건이고, 플랫폼 터치 슬롭(약 8px) 이전인 6px 에서 판정한다. 놓치면 `!event.cancelable` 을 보고 기존 동작에 양보한다. React 18 이 `touchmove` 를 passive 로 등록하므로 리스너는 노드에 직접 `passive: false` 로 붙인다.

## 첫 판정 규칙이 비대칭이었다

처음 쓴 규칙은 아래 방향만 스크롤 위치를 보고, 위 방향은 시트가 더 올라갈 수 있는지(`canDragUp`)만 봤다. 중간 단계에서 목록이 양쪽 다 막혔다 — 위로 밀면 `canDragUp` 이 true 라 시트가 가져가고, 아래로 밀면 `scrollTop` 이 0 이라 또 시트가 가져간다. 카페가 많아 스크롤이 필요한 목록인데 스크롤이 전혀 되지 않았다.

규칙을 대칭으로 바꿨다. **그 방향으로 더 스크롤할 여지가 남아 있으면 스크롤이 우선.** 끝까지 간 뒤에야 시트 드래그로 넘어간다.

고치고 나니 다음 게 나왔다. 시트 박스는 항상 full 높이이고 `translateY` 로만 노출량을 줄인다. 중간 단계에서는 목록 아래쪽 `snapOffsets[snap]` px 가 화면 밖에 있고, 스크롤이 되기 시작하자 끝까지 내려도 그 영역의 항목이 보이지 않았다. 잘린 만큼의 여백 요소를 목록 끝에 뒀다. padding 은 브라우저에 따라 `scrollHeight` 에 잡히지 않아 요소로 넣었다.

## 마커 200개를 그리는 경로

리스트가 상시로 떠 있으면 지도와 목록이 같은 데이터를 동시에 그린다. 매 프레임 반복되던 작업을 걷어냈다.

- 마커의 selected 아이콘을 지연 생성으로 바꿨다. 선택되는 마커는 하나인데 전량 미리 만들면 마커당 약 5.5KB SVG 문자열이 버려진다
- `getPlaceScore` 결과를 `ratings` 배열 identity 기준 WeakMap 에 캐시했다
- scroll 핸들러를 `requestAnimationFrame` 으로 묶어 강제 레이아웃 반복을 없앴다
- 장소 검색에 250ms 디바운스를 걸고, 피드 드로어는 열려 있을 때만 쿼리하게 했다
- `getOpenStatus` 가 `now` 를 인자로 받게 해 목록에서 dayjs 객체가 항목마다 새로 만들어지는 걸 막았다
- 공지 뱃지의 localStorage 읽기를 마운트 후 1회로 옮겼다. 시크릿 모드에서 throw 하는 것도 같이 처리된다

**전후를 수치로 재지는 않았다.** 프레임 타임이나 렌더 횟수를 측정한 게 아니라, 마커 200개 경로에서 반복 호출되는 지점을 코드로 짚어 걷어낸 것이다.

## 현재위치는 단발 요청으로 잡히지 않았다

같이 나온 문제. 안드로이드는 첫 측위가 느려서 `getCurrentPosition` 단발 요청이 공급자가 예열되는 동안 타임아웃으로 죽고, 직후에 도착했을 좌표를 버린다. 실기기 크롬에서 "시간이 오래 걸려요"가 여러 번 뜨다가 결국 잡히는 증상으로 확인했다.

`watchPosition` 으로 듣다가 첫 좌표가 오면 즉시 `clearWatch` 하고 반환한다. 개별 타임아웃은 없애고 전체 제한을 20초로 일원화했다 — 예열 중의 일시적 실패로 감시가 끊기면 기다리면 잡혔을 좌표를 놓친다. `PERMISSION_DENIED` 만 즉시 끝내고 나머지 에러에서는 감시를 유지한다. `enableHighAccuracy` 는 false 로 뒀다. GPS 단독 측위를 강제하면 실내 콜드 스타트가 더 느려진다.

인앱 브라우저에서 실패하면 안내 문구를 바꿨다. "실외로 나가라"가 아니라 기본 브라우저로 열라고 해야 맞다.

## 남은 것

시트 드래그 엔진은 여전히 두 개다. 하나는 높이 기반 2단계, 하나는 offset 기반 3단계에 속도를 본다. 판정 계층을 공유하게 만들었을 뿐 모델을 합치지는 않았다.

탭을 넣는 일이 화면 16개를 건드리는 일이 된 건, 지도 위에 전부 얹어둔 구조에서는 무엇 하나를 새로 놓을 자리가 없었기 때문이다.
