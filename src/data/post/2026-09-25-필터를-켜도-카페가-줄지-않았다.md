카공지도의 카페 1,061곳에는 `studyCafeMeta` 라는 필드가 붙어 있다. 좌석이 편한지, 화장실이 깨끗한지, 주차가 되는지, 단체석이 있는지. 지도 상단 필터가 이 값을 읽는다.

필터를 켜도 목록이 거의 줄지 않았다. 좌석·화장실 같은 항목은 90% 이상이 `true` 였다.

## 리뷰 한 줄이면 true였다

값을 만든 건 GPT였다. 리뷰를 읽고 항목별로 판단하게 했는데, 리뷰 200개 중 한 번이라도 "좌석이 편했다"는 말이 나오면 `true` 로 답한다. 틀린 답은 아니다. 질문이 "이 카페에 좌석이 편하다는 언급이 있는가"에 가까웠고 GPT는 그 질문에 정확히 답했다.

필터에 쓰려면 다른 질문이어야 했다. "이 카페가 좌석으로 상위 몇 %인가."

## 네이버 키워드 투표로 바꿨다

네이버 플레이스에는 방문자가 누른 키워드 투표가 있다. "좌석이 편해요", "화장실이 깨끗해요" 같은 항목과 각각의 표 수, 그리고 전체 투표 수. 크롤링할 때 `naverKeywords` 로 같이 저장하도록 하고, 판단을 코드 규칙으로 옮겼다.

```ts
// src/crawler/studyCafeMeta/keywordMetaRules.ts
export const KEYWORD_META_RULES = {
  hasComfortableSeats: { keywords: ['좌석이 편해요'], minRatio: 4, minVotes: 10 },
  hasCleanRestroom:    { keywords: ['화장실이 깨끗해요'], minRatio: 2, minVotes: 10 },
  hasGoodValueDrinks:  { keywords: ['가성비가 좋아요'], minRatio: 3, minVotes: 10 },
  hasParking:          { keywords: ['주차하기 편해요'], minRatio: 1, minVotes: 5 },
  hasGroupSeats:       { keywords: ['단체모임 하기 좋아요', '룸이 잘 되어있어요'], minRatio: 0, minVotes: 3 },
};
```

기준이 두 개인 이유는 한 개로는 안 되기 때문이다. 표 수만 보면 리뷰가 많은 카페가 전부 통과한다. 비율만 보면 표가 서너 개뿐인 카페가 100%로 올라온다. 비율과 최소 표 수를 같이 걸어 상위 20~30%가 남게 맞췄다.

비율 기준이 항목마다 다른 건 키워드마다 눌리는 빈도가 달라서다. "주차하기 편해요"는 애초에 잘 안 눌리고, "단체모임 하기 좋아요"는 표 자체가 적어 비율 기준을 두면 아무도 통과하지 못한다.

| 항목 | 판단 주체 | 기준 |
|---|---|---|
| 좌석·화장실·가성비·주차 | 키워드 투표 | 비율 + 최소 표 수 |
| 단체석 | 키워드 투표 | 표 수만 |
| 심야 운영 | 영업시간 | 24시간 또는 새벽 2시 이후 마감 |
| 와이파이·시간제한 | GPT | 대응하는 네이버 키워드가 없다 |
| 카공 점수(분위기·콘센트·자리·기타) | GPT | 기존 채점 기준 그대로 |

투표가 하나도 없는 카페는 GPT 결과를 그대로 둔다. 덮어쓸 근거가 없다.

## 분위기는 비율만 봤다

카공지도에 올라온 카페는 이미 전부 카공하기 좋은 곳이다. 그래서 데이트 분위기 항목(`goodForDate`)은 절대 표 수가 아니라 분위기 키워드가 전체 투표에서 차지하는 비율로 판단했다 — 20% 이상이면서 50표 이상. 약 상위 20%가 남는다.

```ts
const DATE_KEYWORD_PATTERN = /인테리어|아늑|사진|뷰가|데이트|분위기가 좋|특별한 날|로맨틱/;
```

"대화하기 좋아요"는 뺐다. 거의 모든 카페에 많이 눌려 있어서 넣으면 변별이 사라진다.

리뷰 원문은 저장하지 않으므로 리뷰에 나온 언급 수는 쓰지 않았다. 크롤링 시점과 나중에 재계산한 결과가 달라지면 안 된다.

## 영업시간은 어느 줄을 읽을지가 문제였다

심야 운영은 GPT에게 묻지 않고 영업시간에서 계산한다. 24시까지거나, 마감이 시작보다 이르면서 새벽 2시 이후면 `true`.

문제는 네이버 상세 응답의 `newBusinessHours` 가 서비스 타입별 배열이라는 점이었다. 스타벅스는 매장·드라이브스루·워크스루·딜리버스 네 개가 들어 있고, 드라이브스루와 워크스루는 시간이 전부 `null` 이다. 매장이 항상 첫 번째라 `[0]` 을 쓴다.

## 크롤러도 같이 고쳤다

- 리뷰를 커서 페이지네이션으로 최대 4페이지, 페이지당 50개 — 카페당 최대 200개
- 가게 ID(`naverPlace`)를 저장해 다음 실행에서 검색 단계를 건너뛴다
- 상세 페이지 SSR 데이터에서 영업시간과 첫 번째 대표 이미지를 뽑는다
- "어바웃 AI" 리뷰 본문을 카공 관점 요약으로 저장한다. 카공 점수 GPT는 점수만 저장하고 채점 기준은 건드리지 않았다

전체 재평가용 스크립트(`npm run crawl:all`)는 AppModule 대신 DB와 PlaceModule 만 올린다. 스케줄러와 Bull/Redis 가 같이 뜰 이유가 없다. 그리고 몇 시간짜리 작업이 네트워크 오류 하나로 죽지 않도록 `uncaughtException` 과 `unhandledRejection` 을 로그만 남기고 넘긴다. 중단되면 `CRAWL_SKIP_CRAWLED_SINCE` 로 이어서 돌린다.

## 결과

전체 재평가는 96분 걸렸고 1,061곳 중 1,039곳이 처리됐다. 로그에는 치명적 실패가 없었다. 남은 22곳이 왜 빠졌는지는 확인하지 않았다.

와이파이와 시간제한은 여전히 GPT 판단이다. 대응하는 네이버 키워드가 없어 같은 방식으로 옮길 수 없었다.

필터를 만들 때 필요한 건 "이 카페에 그런 언급이 있는가"가 아니라 "다른 카페와 비교해 어디쯤인가"였다. 첫 번째 질문은 GPT가 이미 정확히 답하고 있었다.
